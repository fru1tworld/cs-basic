# 병렬 조인과 집계

조인할 데이터가 많으면 한 스레드가 모든 행을 처리하는 데 오래 걸린다. 병렬 조인은 이 작업을 여러 프로세서나 스레드에 나누어 실행한다. 현대 데이터베이스는 이처럼 단일 쿼리 안의 일을 나누는 Intra-Query Parallelism으로 멀티코어 CPU를 활용하고 응답 시간을 줄인다.

## 병렬 처리 유형

Query1, Query2, Query3처럼 서로 다른 쿼리를 동시에 실행하는 것은 Inter-Query Parallelism이다. 이에 비해 Intra-Query Parallelism은 Query 1 하나의 작업을 Work1, Work2, Work3으로 나누어 여러 워커가 처리한다.

단일 쿼리 안에서도 나누는 기준이 다르다. 하나의 연산자를 여러 워커가 처리하면 Intra-Operator 병렬화이고, 여러 연산자를 파이프라인으로 연결해 동시에 처리하면 Inter-Operator 병렬화다.

## 데이터 분배 전략

- 데이터 파티셔닝 전략
- Range Partitioning
- A-F, G-L, M-R, S-Z
- Worker1 Worker2 Worker3 Worker4
- 장점: 범위 쿼리에 유리
- 단점: 데이터 편향 가능
- Hash Partitioning
- hash%4=0 hash%4=1 hash%4=2 hash%4=3
- Worker1, Worker2, Worker3, Worker4
- 장점: 균등 분배, 등가 조인에 최적
- 단점: 범위 쿼리 비효율
- Round-Robin Partitioning
- Row 1 → Worker1
- Row 2 → Worker2
- Row 3 → Worker3
- Row 4 → Worker1 ...
- 장점: 완벽한 균등 분배
- 단점: 조인에 비효율적 (전체 브로드캐스트 필요)
- Broadcast
- 작은 테이블을 모든 워커에 복제
- Full, Full, Full, Full, ← 작은 테이블
- Copy, Copy, Copy, Copy
- Worker1 Worker2 Worker3 Worker4

## 병렬 Hash Join

- Parallel Hash Join
- Phase 1: Parallel Build
- Build Table (Partitioned)
- Part1, Part2, Part3, Part4
- Hash, Hash, Hash, Hash, Build Workers
- Table1, Table2, Table3, Table4
- Phase 2: Parallel Probe
- Probe Table (Partitioned by same key)
- Part1, Part2, Part3, Part4
- Probe, Probe, Probe, Probe, Probe Workers
- Work1, Work2, Work3, Work4
- Gather

```sql
-- PostgreSQL 병렬 Hash Join 예시
SET max_parallel_workers_per_gather = 4;
SET parallel_tuple_cost = 0.01;
SET parallel_setup_cost = 100;

EXPLAIN (ANALYZE, VERBOSE)
SELECT o.*, c.name
FROM orders o
JOIN customers c ON o.customer_id = c.id
WHERE o.order_date > '2024-01-01';

/*
Gather  (actual time=50.0..150.0 rows=100000)
  Workers Planned: 4
  Workers Launched: 4
  ->  Parallel Hash Join  (actual time=40.0..100.0 rows=25000 loops=5)
        Hash Cond: (o.customer_id = c.id)
        ->  Parallel Seq Scan on orders o  (actual time=0.1..30.0 rows=50000 loops=5)
              Filter: (order_date > '2024-01-01')
        ->  Parallel Hash  (actual time=20.0..20.0 rows=10000 loops=5)
              ->  Parallel Seq Scan on customers c  (actual time=0.1..10.0 rows=10000 loops=5)
*/
```

## 병렬 Merge Join

- Parallel Merge Join
- 방법 1: Parallel Sort + Sequential Merge
- Table R, Table S
- Part1, Part1
- Part2, Part2
- Part3, Part3
- Part4, Part4
- Parallel Sort, Parallel Sort
- Sorted, Sorted
- R, S
- Merge
- 방법 2: Range Partition + Parallel Merge
- R (Range Part), S (Range Part)
- 1-100, Merge →, 1-100, → Worker1
- 101-200, Merge → 101-200, → Worker2
- 201-300, Merge → 201-300, → Worker3
- 301-400, Merge → 301-400, → Worker4
- 각 파티션 내에서 독립적으로 Merge 수행

## 병렬 Nested Loop Join

- Parallel Nested Loop Join
- Outer Table을 파티셔닝, Inner Table은 모든 워커가 접근
- Outer Table (orders)
- Part1, Part2, Part3, Part4
- Worker, Worker, Worker, Worker
- 1, 2, 3, 4
- Inner Table, ← 인덱스 사용
- (customers), 모든 워커가 공유 접근
- 적합한 경우:
- Outer가 크고, Inner에 인덱스가 있는 경우
- 각 Outer 행당 소수의 Inner 행만 매칭

```sql
-- PostgreSQL Parallel Nested Loop
EXPLAIN (ANALYZE)
SELECT o.*, c.name
FROM orders o
JOIN customers c ON o.customer_id = c.id
WHERE o.amount > 1000;

/*
Gather  (actual time=1.0..50.0 rows=5000)
  Workers Planned: 2
  Workers Launched: 2
  ->  Nested Loop  (actual time=0.5..40.0 rows=1667 loops=3)
        ->  Parallel Seq Scan on orders o  (actual time=0.1..10.0 rows=1667 loops=3)
              Filter: (amount > 1000)
        ->  Index Scan using customers_pkey on customers c  (actual time=0.01..0.01 rows=1 loops=5000)
              Index Cond: (id = o.customer_id)
*/
```

## PostgreSQL 병렬 처리 아키텍처

- PostgreSQL Parallel Query
- Client
- Leader Process
- (Backend that received query)
- Worker 1, Worker 2, Worker 3
- (bgworker), (bgworker), (bgworker)
- Gather Node
- 워커 결과 수집
- tuple queue 기반 통신
- 관련 파라미터:
- max_parallel_workers = 8
- max_parallel_workers_per_gather = 2
- min_parallel_table_scan_size = 8MB
- min_parallel_index_scan_size = 512kB
- parallel_tuple_cost = 0.1
- parallel_setup_cost = 1000

## 병렬 집계 (Parallel Aggregation)

병렬 집계는 각 워커가 부분 결과를 구하는 Partial Aggregate와 Leader가 이를 합치는 Finalize Aggregate로 나뉜다. 평균을 구하려면 각 워커가 합계와 개수를 함께 전달한다.

| 워커 | SUM(x) | COUNT(*) |
| --- | --- | --- |
| Worker1 | 100 | 10 |
| Worker2 | 150 | 15 |
| Worker3 | 120 | 12 |

Leader는 합계를 `100 + 150 + 120 = 370`, 개수를 `10 + 15 + 12 = 37`로 모은 뒤 `AVG = 370 / 37 = 10`을 계산한다. 실행 계획에서는 Parallel Seq Scan 위에 Partial Aggregate가 놓이고, Gather가 3개 워커의 결과를 모아 Finalize Aggregate로 전달하는 흐름을 볼 수 있다.

```sql
-- 병렬 GROUP BY 예시
EXPLAIN (ANALYZE)
SELECT dept_id, AVG(salary)
FROM employees
GROUP BY dept_id;

/*
Finalize GroupAggregate  (actual time=100.0..110.0 rows=50)
  Group Key: dept_id
  ->  Gather Merge  (actual time=90.0..100.0 rows=150)
        Workers Planned: 3
        Workers Launched: 3
        ->  Sort  (actual time=80.0..82.0 rows=50 loops=4)
              Sort Key: dept_id
              ->  Partial HashAggregate  (actual time=70.0..75.0 rows=50 loops=4)
                    Group Key: dept_id
                    ->  Parallel Seq Scan on employees  (actual time=0.1..50.0 rows=25000 loops=4)
*/
```
