# 쿼리 컴파일

SQL은 필요한 결과를 선언하지만, 그 결과를 얻기 위한 실행 방법까지 지정하지는 않는다. DBMS는 Parsing → Binding → Optimization → Code Generation 과정을 거쳐 SQL을 실행 계획으로 바꾼다. 각 단계가 맡은 일을 구분하면 문법 오류와 이름 해석 오류가 어디서 발생하는지, 옵티마이저가 언제 실행 방법을 선택하는지 이해할 수 있다.

## 쿼리 처리 파이프라인

SQL을 받은 Parser는 구문을 분석해 AST를 만든다. Binder 또는 Analyzer가 이름과 의미를 해석하면 논리적 계획(Logical Plan)을 구성할 수 있다. 이어 Rewriter가 뷰를 확장하고 쿼리를 재작성하며, Optimizer가 비용을 비교해 물리적 계획(Physical Plan)을 선택한다. Executor는 이 계획을 실행해 결과를 반환한다.

## Parsing (구문 분석)

- SQL 문자열을 AST(Abstract Syntax Tree)로 변환:

- Parsing
- 입력: SELECT name, salary FROM employees WHERE dept_id = 10
- Lexical Analysis (어휘 분석)
- 토큰화: [SELECT] [name] [,] [salary] [FROM] ...
- Syntax Analysis (구문 분석)
- 문법 검사, AST 생성
- 결과 AST:
- SelectStatement
- SelectList, FromClause, WhereClause
- Column Column, TableRef, Comparison
- "name" "salary" "employees", /, \
- Column, Literal
- "dept_id", 10
- 오류 감지:
- 문법 오류: "SELEC \* FROM t" → syntax error
- 괄호 불일치, 키워드 오타 등

## Binding / Semantic Analysis (의미 분석)

- AST의 이름을 실제 데이터베이스 객체에 연결:

- Binding
- 수행 작업:
- 이름 해석 (Name Resolution)
- "employees" → schema.employees (OID: 12345)
- "name" → employees.name (column index: 1, type: text)
- "salary" → employees.salary (column index: 3, type: int)
- 타입 검사 (Type Checking)
- dept_id = 10 → 정수 비교 OK
- dept_id = 'abc' → 타입 오류 또는 암시적 변환
- 권한 검사 (Permission Check)
- 현재 사용자가 employees 테이블 SELECT 권한 있는지
- 스코프 해석
- 서브쿼리의 컬럼 참조 범위 결정
- 상관 서브쿼리의 외부 참조 식별
- 결과: Bound AST (모든 참조가 해석됨)
- 오류 감지:
- "테이블이 존재하지 않음"
- "컬럼 'nam'을(를) 찾을 수 없음"
- "권한이 없음"

## Query Rewriter (쿼리 재작성)

- Query Rewriting
- 뷰 확장 (View Expansion)
- CREATE VIEW active_emp AS
- SELECT \* FROM employees WHERE status = 'active';
- SELECT name FROM active_emp WHERE dept_id = 10;
- SELECT name FROM employees
- WHERE status = 'active' AND dept_id = 10;
- 서브쿼리 평탄화 (Subquery Flattening)
- SELECT \* FROM a WHERE id IN (SELECT a_id FROM b);
- SELECT DISTINCT a.\* FROM a JOIN b ON a.id = b.a_id;
- 상수 폴딩 (Constant Folding)
- WHERE created_at > '2024-01-01' + INTERVAL '30 days'
- WHERE created_at > '2024-01-31'
- 불필요한 조건 제거
- WHERE 1 = 1 AND name = 'Kim'
- WHERE name = 'Kim'

## Logical Plan vs Physical Plan

논리적 계획은 무엇을 계산할지 관계 대수 연산자 트리로 나타낸다. 예를 들어 `Scan(employees)`에서 `Select(dept_id = 10)`으로 행을 고르고 `Project(name, salary)`로 컬럼을 선택한다. 이 단계에서는 물리적으로 어떤 방법을 사용할지 정하지 않는다.

물리적 계획은 같은 계산을 수행할 구체적인 알고리즘을 지정한다. 위 예에서는 `IndexScan(employees, idx_dept_id, dept_id = 10)`으로 조건에 맞는 행을 찾은 뒤 `Project(name, salary)`를 수행할 수 있다. 옵티마이저는 논리적 계획을 구현하는 여러 물리적 계획 중 하나를 선택한다.

## 옵티마이저 개요

- Optimizer
- Rule-Based Optimization (규칙 기반):
- 항상 적용되는 변환 규칙
- Predicate Pushdown
- Projection Pushdown
- 불필요한 연산 제거
- Cost-Based Optimization (비용 기반):
- 여러 대안 중 비용이 가장 낮은 선택
- 통계 정보 필요 (행 수, 카디널리티, 분포)
- 결정 사항:
- 접근 방법: Seq Scan vs Index Scan
- 조인 방법: Nested Loop vs Hash vs Merge
- 조인 순서: (A ⋈ B) ⋈ C vs A ⋈ (B ⋈ C)
- 정렬 방법: 인덱스 활용 vs Sort 연산
- 탐색 공간:
- N개 테이블 조인: N! 가지 순서
- 각각에 여러 알고리즘 적용 가능
- 탐색 공간 폭발 → 휴리스틱 필요

## Prepared Statement와 Plan Caching

- Prepared Statement
- 일반 쿼리:
- Parse → Bind → Optimize → Execute (매번 반복)
- Prepared Statement:
- PREPARE stmt AS SELECT \* FROM t WHERE id = \$1;
- Parse → Bind (파라미터 제외) → 저장
- EXECUTE stmt(123);
- 파라미터 바인딩 → (필요시 Optimize) → Execute
- 장점:
- Parse 오버헤드 제거
- SQL Injection 방지
- 일부 DBMS: 실행 계획 캐싱
- PostgreSQL Plan Caching:
- 처음 5회: 파라미터별 Custom Plan
- 이후: Generic Plan 사용 여부 결정
- plan_cache_mode 설정으로 제어

```sql
-- PostgreSQL Prepared Statement
PREPARE get_user(int) AS
SELECT * FROM users WHERE id = $1;

EXECUTE get_user(123);
EXECUTE get_user(456);

DEALLOCATE get_user;

-- 실행 계획 확인
EXPLAIN EXECUTE get_user(123);
```

## JIT Compilation

- 일부 DBMS에서 쿼리를 기계어로 컴파일하여 실행:

- JIT Compilation (PostgreSQL 11+)
- 일반 실행:
- Executor → 일반적인 Tuple-at-a-time 인터프리터
- JIT 실행:
- 표현식을 LLVM IR로 컴파일
- 기계어로 변환
- 컴파일된 코드 실행
- JIT 대상:
- WHERE 조건 평가
- Projection 계산
- 집계 함수
- 튜플 역직렬화
- 장점:
- 함수 호출 오버헤드 제거
- CPU 최적화 (SIMD 등)
- 대규모 스캔에서 효과적
- 단점:
- 컴파일 시간 오버헤드
- 작은 쿼리에서는 비효율
- 설정:
- jit = on
- jit_above_cost = 100000, -- 이 비용 이상일 때 JIT
