# 쿼리 실행 모델

실행 계획에 연산자와 순서가 정해져 있어도, 연산자 사이에서 데이터를 한 행씩 넘길지 한꺼번에 넘길지는 별도의 문제다. 이 흐름을 정하는 것이 실행 모델이다. Volcano(Iterator), Materialization, Vectorized Execution은 데이터를 주고받는 단위를 달리해 함수 호출 비용과 메모리 사용량 사이의 균형을 잡는다. 현대 분석 시스템에서는 벡터화 실행과 JIT 컴파일이 주류가 되고 있다.

## Volcano (Iterator) Model

Volcano는 널리 사용되는 전통적인 실행 모델로, 상위 연산자가 하위 연산자에서 튜플을 하나씩 가져오는 Pull-based 방식이다. 각 연산자는 초기화하는 `open()`, 다음 튜플이나 EOF를 반환하는 `next()`, 자원을 정리하는 `close()`를 구현한다.

`SELECT name FROM emp WHERE dept_id = 10`을 예로 들면, 루트인 Project의 `next()` 호출이 Filter의 `next()`로 이어지고 Filter는 SeqScan의 `next()`를 호출한다. SeqScan이 `emp`의 튜플을 반환하면 Filter가 `dept_id = 10`을 검사한다. 조건을 만족하지 않으면 다음 튜플을 요청하고, 만족하면 Project로 넘긴다. Project는 여기서 `name`만 추출해 반환한다.

- 장점:
- 단순한 구현
- 파이프라이닝 (중간 결과 저장 불필요)
- 메모리 효율적

- 단점:
- 함수 호출 오버헤드 (튜플당 여러 번)
- CPU 캐시 비효율
- 가상 함수 호출 오버헤드

## Materialization Model

Materialization 모델에서는 각 연산자가 `output()`으로 전체 결과 집합을 반환한다. SeqScan이 모든 튜플을 모아 Filter에 넘기고, Filter가 조건에 맞는 전체 결과를 Project에 넘기는 흐름이다.

튜플마다 `next()`를 호출하지 않아 구현이 단순하고 함수 호출 횟수도 줄어든다. 대신 연산자 사이의 큰 중간 결과를 저장해야 하므로 메모리를 많이 쓰고 첫 결과를 받기까지 오래 걸린다.

## Vectorized Execution

- Vectorized Execution
- 원칙: Batch-at-a-time (예: 1000개 튜플 단위)
- Volcano와 Materialization의 절충:
- 튜플 단위 → 함수 호출 오버헤드
- 전체 결과 → 메모리 낭비
- 배치 단위 → 균형점
- 구조: 컬럼 단위 배치 (Column Batch)
- Column Batch (1024 rows)
- id:, [1, 2, 3, ..., 1024]
- name:, ["Kim", "Lee", "Park", ...]
- salary:[50000, 60000, 55000, ...]
- valid: [1, 1, 0, 1, ...], (selection)
- 장점:
- 함수 호출 오버헤드 감소 (1024배)
- CPU 캐시 친화적
- SIMD 활용 가능
- 컬럼 압축과 잘 어울림
- 사용: MonetDB, ClickHouse, DuckDB, Snowflake

- 벡터화 연산 예시:

```cpp
// 튜플 단위 (Volcano)
for each tuple t:
    if t.salary > 50000:
        output(t)

// 벡터 단위
for i = 0 to batch_size:
    selection[i] = salary[i] > 50000  // SIMD 가능

// SIMD 활용
__m256i threshold = _mm256_set1_epi32(50000);
__m256i salaries = _mm256_loadu_si256(...);
__m256i result = _mm256_cmpgt_epi32(salaries, threshold);
```

## Push vs Pull

- Push vs Pull Execution
- Pull-based (Volcano):
- Consumer
- next()
- Producer
- 상위 연산자가 하위에게 "다음 데이터 줘" 요청
- 데이터가 위로 끌어올려짐
- Push-based:
- Producer
- produce(tuple)
- Consumer
- 하위 연산자가 상위에게 데이터를 밀어넣음
- 이벤트 기반, 비동기 처리에 적합
- 병렬화, 파이프라이닝에 유리
- Morsel-Driven Parallelism (HyPer):
- Push-based + 작업 단위(Morsel) 분배
- 동적 로드 밸런싱

## Pipeline Breakers

- 특정 연산자는 모든 입력을 받아야 결과를 출력할 수 있음:

- Pipeline Breakers
- Non-Blocking (파이프라이닝 가능):
- Filter: 조건 체크 후 바로 출력
- Project: 컬럼 선택 후 바로 출력
- Nested Loop Join (inner가 작을 때)
- Blocking (파이프라인 끊김):
- Sort: 전체 정렬 후 출력
- Hash Join (Build): 해시 테이블 완성까지 대기
- Aggregation: 전체 그룹화 후 출력
- DISTINCT: 전체 확인 후 출력
- 예시:
- Project
- Pipeline 1
- Sort, ←, (Blocking)
- Filter
- Pipeline 2
- SeqScan ←
- Sort가 Pipeline Breaker: 위아래가 다른 파이프라인

## JIT Compilation (PostgreSQL)

- JIT Compilation
- 일반 실행:
- 범용 인터프리터로 연산자 트리 순회
- 각 표현식마다 함수 호출
- JIT 실행:
- 쿼리별 특화 코드 생성
- LLVM을 사용하여 기계어로 컴파일
- JIT 대상 (PostgreSQL):
- Expression Evaluation
- WHERE a + b > c \* 2 → 특화 코드
- Tuple Deforming
- 튜플 → 컬럼 값 추출 코드
- Aggregation
- SUM, COUNT 등 집계 루프
- 효과:
- 함수 호출 오버헤드 제거
- 인라인화, 상수 폴딩
- OLAP 쿼리에서 2-5배 성능 향상
- 비용:
- 컴파일 시간 (수십~수백 ms)
- 작은 쿼리에서는 오히려 느림

```sql
-- PostgreSQL JIT 설정
SET jit = on;
SET jit_above_cost = 100000;  -- 이 비용 이상에서 JIT
SET jit_inline_above_cost = 500000;
SET jit_optimize_above_cost = 500000;

-- JIT 사용 확인
EXPLAIN (ANALYZE) SELECT SUM(amount) FROM large_table;
-- JIT:
--   Functions: 4
--   Generation Time: 1.234 ms
--   Inlining Time: 5.678 ms
--   Optimization Time: 10.123 ms
--   Emission Time: 15.456 ms
```

## 실행 모델 비교

- 실행 모델 비교
- Volcano, Materialization, Vectorized
- 단위, Tuple, Entire Set, Vector/Batch
- 메모리, 낮음, 높음, 중간
- 함수 호출, 많음, 적음, 적음
- 캐시 효율, 낮음, 중간, 높음
- SIMD, 어려움, 가능, 최적
- 적합 워크로드, OLTP, 작은 쿼리, OLAP
- 사용 시스템, PostgreSQL,, SQLite,, MonetDB
- MySQL, 일부 임베디드, ClickHouse
- DuckDB
