# 힙 파일과 빈 공간 관리

힙 파일(Heap File)은 튜플을 순서 없이 저장하는 기본적인 파일 조직 방식이다. 정렬 위치를 유지할 필요가 없으므로 새 레코드는 빈 공간이 있는 페이지에 삽입한다. PostgreSQL은 이를 기본 테이블 저장 방식으로 사용한다. MySQL InnoDB는 클러스터링 인덱스를 기본으로 사용하지만, 내부적으로는 힙과 유사하게 페이지의 빈 공간을 관리한다.

## 힙 파일 vs 정렬 파일

- Heap File
- 5, 2, 8, 1, 순서 없이 저장
- 3, 9, 4, 7
- 삽입: O(1) - 빈 공간에 바로 삽입
- 검색: O(N) - 전체 스캔 필요
- 삭제: O(N) + O(1) - 찾고 삭제 표시
- Sorted File
- 1, 3, 5, 8, 정렬 순서로 저장
- 2, 4, 6, 9
- 삽입: O(N) - 정렬 위치 찾고 이동
- 검색: O(log N) - 이진 탐색 가능
- 범위 검색: 효율적 (연속 페이지)

- Page 1, → Page 2, → Page 3, → Page 4, → ...

## 빈 공간 관리 (Free Space Management)

Free List는 빈 페이지를 연결 리스트로 관리한다. 예를 들어 `Header → Page 2 → Page 5 → Page 8 → NULL`이라면 삽입할 때 이 목록에서 페이지를 가져오고, 삭제로 페이지가 비면 목록에 돌려놓는다. 다만 빈 페이지 자체를 연결하는 방식만으로는 일부 공간이 남은 페이지를 관리하기 어렵다.

Free Space Map(FSM)은 페이지마다 남은 공간을 기록해 이 문제를 다룬다.

| Page ID | 남은 공간(bytes) | 상태 |
| --- | --- | --- |
| 0 | 200 | 일부 사용 |
| 1 | 4000 | 일부 사용 |
| 2 | 0 | 가득 참 |
| 3 | 1500 | 일부 사용 |
| 4 | 8000 | 비어 있음 |

100B 튜플을 삽입하려면 FSM에서 100B 이상의 빈 공간이 있는 페이지를 찾는다. 페이지 전체가 비어 있지 않아도 남은 공간을 활용할 수 있다.

## PostgreSQL Free Space Map

- PostgreSQL FSM Structure
- FSM은 별도 파일 (relation_fsm)
- 구조: 3-level tree
- [Root FSM Page]
- [Upper Page] [Upper Page] [Upper Page]
- [Leaf Pages] [Leaf Pages] [Leaf Pages]
- 각 페이지의 빈 공간을 1 byte (256 카테고리)로 표현
- 0 = full, 255 = empty
- 조회: Root부터 내려가며 충분한 공간 가진 페이지 찾기
- 갱신: 페이지 변경 시 FSM 갱신

```sql
-- PostgreSQL: FSM 정보 확인
CREATE EXTENSION pg_freespacemap;

SELECT * FROM pg_freespace('mytable');
```

- `pg_freespace` 결과 예시:
  - `blkno=0`: `avail=2048`
  - `blkno=1`: `avail=4096`
  - `blkno=2`: `avail=0`

## Visibility Map (VM)

- PostgreSQL Visibility Map
- 각 페이지당 2 bits:
- Bit 1: All-Visible (모든 튜플이 모든 트랜잭션에 보임)
- Bit 2: All-Frozen (모든 튜플이 Frozen 상태)
- 용도:
- Index-Only Scan: VM 체크로 힙 방문 회피
- VACUUM: All-visible 페이지 스킵
- Anti-Wraparound: All-frozen 페이지 스킵
- Page 0: [1,0] - All-visible, not frozen
- Page 1: [0,0] - Has dead tuples
- Page 2: [1,1] - All-visible and frozen
- Page 3: [1,0] - All-visible, not frozen

```sql
-- VM 확인
CREATE EXTENSION pg_visibility;

SELECT * FROM pg_visibility_map('mytable');
```

- `pg_visibility_map` 결과 예시:
  - `blkno=0`: `all_visible=t`, `all_frozen=f`
  - `blkno=1`: `all_visible=f`, `all_frozen=f`

## TOAST (The Oversized-Attribute Storage Technique)

- TOAST
- 원본 테이블, TOAST 테이블
- id, name, bio_ptr, →, chunk_id, chunk_data
- 1, Kim, (toast), 1, [blob...]
- 2, Lee, (toast), 2, [blob...]
- TOAST 전략:
- PLAIN: TOAST 안 함
- EXTENDED: 압축 후 외부 저장 (기본값)
- EXTERNAL: 압축 없이 외부 저장
- MAIN: 압축만, 외부 저장은 최후
- 압축 알고리즘: pglz (기본), lz4 (PostgreSQL 14+)

```sql
-- TOAST 전략 변경
ALTER TABLE mytable ALTER COLUMN bio SET STORAGE EXTERNAL;

-- TOAST 테이블 확인
SELECT relname, reltoastrelid::regclass
FROM pg_class WHERE relname = 'mytable';
```

## Overflow Pages (MySQL InnoDB)

- InnoDB Overflow Pages
- ROW_FORMAT=COMPACT/REDUNDANT:
- VARCHAR/BLOB 768B까지 인라인
- 초과분은 overflow page
- ROW_FORMAT=DYNAMIC (기본, 5.7+):
- 긴 컬럼은 20B 포인터만 인라인
- 전체 데이터는 overflow page
- Main Page, Overflow Pages
- id, name, ptr, →, [full data...]
- 1, Kim, →

## 힙 파일의 삭제 처리

레코드를 삭제할 때는 먼저 튜플 헤더에 삭제 표시를 남기고 물리적 공간은 유지한다. PostgreSQL은 `xmax`를 설정하고, MySQL은 delete mark flag를 사용한다.

이 공간을 재사용하려면 별도의 정리가 필요하다. PostgreSQL에서는 VACUUM이 정리한 뒤 FSM을 갱신하고, MySQL에서는 purge thread가 정리한다. 페이지 안에 흩어진 빈 공간은 compaction으로 모은다. 이와 관련된 동작으로 PostgreSQL의 HOT pruning과 VACUUM, MySQL의 page reorganization이 있다.
