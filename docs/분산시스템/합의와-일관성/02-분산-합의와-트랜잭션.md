# 분산 합의와 트랜잭션

## 분산 시스템 기초 개념

### 분산 시스템이란?

분산 시스템은 네트워크로 연결된 독립적인 컴퓨터들이 하나의 시스템처럼 동작하는 환경이다. 예를 들어 Node A, B, C가 각각 애플리케이션과 DB를 실행하고, 네트워크로 메시지를 주고받으며 작업을 함께 처리한다.

### 분산 시스템의 특성

#### CAP 정리 (CAP Theorem)

네트워크가 분할되면 선형화 가능한 일관성과 모든 정상 노드에서의 요청 완료를 동시에 보장할 수 없다. 여기서 일관성(C)은 읽기와 쓰기가 실시간 순서를 따르는 하나의 복사본처럼 보인다는 뜻이다. 모든 노드의 물리적인 값이 매 순간 같아야 한다는 의미는 아니다.

분할 상황에서 일관성을 우선하면 일부 요청을 거절하거나 기다리게 해야 한다. 반대로 응답을 계속 제공하면 서로 다른 값을 관찰할 수 있다. 실제 보장은 복제 구성, 읽기·쓰기 옵션, 실패 처리 정책에 따라 달라지므로 PostgreSQL, MySQL, MongoDB, Cassandra, DynamoDB, HBase, ZooKeeper, CouchDB, DNS를 제품 이름만으로 CP·AP·CA에 고정 분류해서는 안 된다. 구체적인 조건은 [CAP와 일관성 모델](01-CAP와-일관성-모델.md)에서 살펴본다.

### 분산 시스템의 도전 과제

노드 사이에서는 메시지가 유실되거나 중복되고 도착 순서가 바뀔 수 있다. 각 노드의 시계도 어긋날 수 있어, 사건의 순서를 다룰 때 논리적 시계나 벡터 시계를 사용한다. 일부 노드만 멈추는 부분 장애나 잘못된 동작을 하는 Byzantine 장애도 고려해야 한다.

이런 조건에서 리더를 선출하고 상태 머신을 복제하려면 합의가 필요하다. 데이터를 여러 노드에 복제할 때는 충돌 해결과 일관성 모델을 정해야 하며, 처리량을 늘릴 때는 수평 확장, 로드 밸런싱, 파티셔닝을 함께 고려한다.

### 시간과 순서 (Time and Ordering)

- 분산 시스템에서 시간 동기화는 매우 어려운 문제임.

#### 논리적 시계 (Logical Clocks)

- Lamport 논리적 시계
- Process A, Process B, Process C
- (1)
- →(2)
- (3)
- →(3)
- (4)
- ← (5)
- (6)
- 규칙:
- 로컬 이벤트 발생 시: LC = LC + 1
- 메시지 전송 시: LC = LC + 1, 메시지에 LC 포함
- 메시지 수신 시: LC = max(LC, 수신된 LC) + 1

#### 벡터 시계 (Vector Clocks)

- 벡터 시계
- Server A, Server B, Server C
- [1,0,0]
- [1,1,0]
- [1,1,1]
- [2,0,0]
- [2,1,1]
- 벡터 시계 비교:
- [1,2,0] < [1,2,1] (인과 관계 있음)
- [1,2,0], [0,1,2] (동시 발생, 인과 관계 없음)

## 분산 합의 알고리즘

### 합의 문제란?

- 분산 시스템에서 합의(Consensus)는 여러 노드가 하나의 값에 동의하는 것을 의미함.

- 합의 문제 예시
- 제안자들, 합의 결과
- Node A, "값 = 5"
- →, 모든 노드가
- Node B, "값 = 7", 동일한 값에
- 동의: "값 = 5"
- Node C, "값 = 5"
- 합의의 조건:
- 종료성(Termination): 모든 올바른 노드는 결국 결정함
- 합의(Agreement): 모든 올바른 노드는 같은 값을 결정함
- 유효성(Validity): 결정된 값은 어떤 노드가 제안한 값임

### Paxos 알고리즘

- Paxos는 Leslie Lamport가 제안한 분산 합의 알고리즘임.

#### Paxos의 역할

- Paxos 역할 구성
- Proposer, 값을 제안하는 역할
- (제안자), 고유한 제안 번호(proposal number) 사용
- Acceptor, 제안을 수락/거부하는 역할
- (수락자), 과반수(Quorum)가 수락해야 합의 성립
- Learner, 합의된 값을 학습하는 역할
- (학습자), 최종 결정값을 적용

#### Paxos 프로토콜 흐름

- Paxos 2단계 프로토콜
- Phase 1: Prepare (준비)
- Proposer, Acceptors
- A1, A2, A3
- Prepare(n), →
- Prepare(n), →
- Prepare(n), →
- ←, Promise(n)
- ←, Promise(n)
- ←, Promise(n)
- Phase 2: Accept (수락)
- Proposer, Acceptors
- A1, A2, A3
- Accept(n,v), →
- Accept(n,v), →
- Accept(n,v), →
- ←, Accepted(n,v)
- ←, Accepted(n,v)
- ←, Accepted(n,v)
- 과반수 수락 → 값 v가 선택됨(Chosen)

#### Paxos 상세 동작 예시

- Paxos 충돌 해결 시나리오
- 시간 →
- Proposer 1 (P1), Proposer 2 (P2)
- 값 = "X", 값 = "Y"
- Prepare(1), →
- Prepare(2), →
- Acceptors: "1보다 높은
- 제안만 수락하겠다"
- ←, Promise(1)
- ←, Promise(2)
- Accept(1,"X"), →
- 불가 거부됨
- (이미 2를 약속함)
- Accept(2,"Y"), →
- 가능 수락됨
- 값 "Y" 선택됨

## 분산 트랜잭션

### 분산 트랜잭션의 필요성

서로 다른 서버에 있는 A 계좌와 B 계좌 사이에서 100원을 이체한다고 해 보자. A의 잔액은 1000원에서 900원으로, B의 잔액은 500원에서 600원으로 바뀌어야 한다. 그런데 A에서 출금한 뒤 B의 입금에 실패하면 100원이 사라진 상태가 된다. 두 변경을 함께 성공시키거나 함께 취소해야 하므로 분산 트랜잭션이 필요하다.

### 2PC (Two-Phase Commit)

- 2PC는 분산 트랜잭션을 위한 가장 기본적인 프로토콜임.

- 2PC (Two-Phase Commit)
- Phase 1: Prepare (투표 단계)
- Coordinator, Participant A, Participant B
- PREPARE, →
- PREPARE, →
- ←, VOTE_YES
- ←, VOTE_YES
- Phase 2: Commit (결정 단계)
- Coordinator, Participant A, Participant B
- COMMIT, →
- COMMIT, →
- ←, ACK
- ←, ACK
- 트랜잭션 완료 (Committed)

#### 2PC 실패 시나리오

- 2PC 실패 처리
- 시나리오 1: Participant가 VOTE_NO 응답
- Coordinator, Participant A, Participant B
- PREPARE, →
- PREPARE, →
- ←, VOTE_YES
- ←, VOTE_NO
- ABORT, →
- ABORT, →
- 시나리오 2: Coordinator 장애 (Blocking 문제)
- Coordinator, Participant A, Participant B
- PREPARE, →
- PREPARE, →
- ←, VOTE_YES
- ←, VOTE_YES
- X (장애 발생!)
- Blocked!, Blocked!
- 락 유지 중.., 락 유지 중..

### 3PC (Three-Phase Commit)

- 3PC는 2PC의 블로킹 문제를 해결하기 위해 제안된 프로토콜임.

- 3PC (Three-Phase Commit)
- Phase 1: CanCommit (투표 요청)
- Coordinator, Participants
- CanCommit?, →
- ←, Yes
- Phase 2: PreCommit (사전 커밋)
- Coordinator, Participants
- PreCommit, →
- ←, ACK
- 이 시점에서 참가자는
- 커밋 준비 완료 상태
- Phase 3: DoCommit (최종 커밋)
- Coordinator, Participants
- DoCommit, →
- ←, ACK
- 장점: Coordinator 장애 시 참가자들이 독립적으로 결정 가능
- 단점: 네트워크 분할 시 일관성 문제 발생 가능

### Saga 패턴

- Saga는 장시간 실행되는 분산 트랜잭션을 위한 패턴임.

- Saga 패턴 (보상 트랜잭션)
- 정상 실행 흐름:
- T1, → T2, → T3, → T4, → 완료
- 주문생성, 결제처리, 재고차감, 배송요청
- 실패 시 보상 트랜잭션:
- T1, → T2, → T3, → T4
- 주문생성, 결제처리, 재고차감, X 실패!
- C3 (재고복구)
- C2 (결제취소)
- C1 (주문취소)
- Saga 구현 방식:
- Choreography (이벤트 기반)
- 이벤트, 이벤트
- 서비스A, →, 서비스B, →, 서비스C
- Orchestration (중앙 조정자)
- Orchestrator
- 서비스A, 서비스B, 서비스C

#### Saga Orchestration 상세 흐름

- Saga Orchestration 예시
- 주문 처리 Saga:
- Client
- 주문 요청
- Saga
- Orchestrator
- 주문, 결제, 재고, 배송
- 서비스, 서비스, 서비스, 서비스
- 1.주문생성
- OK
- 2.결제처리
- OK
- 3.재고차감
- OK

- OK
- 트랜잭션 완료

## 분산 락과 리더 선출

### 분산 락 (Distributed Lock)

분산 락은 여러 서버가 공유 자원을 동시에 수정하는 것을 제어한다. 예를 들어 Server A와 B가 모두 재고 10개를 읽고 각각 1개씩 차감한 뒤 9를 저장하면, 기대값인 8이 아니라 9가 남는다. 한쪽의 변경이 사라지는 Lost Update를 막기 위해 접근 순서를 제어해야 한다.

#### Redis를 이용한 분산 락 (Redlock)

- Redis 분산 락 (Redlock)
- 단일 인스턴스 락:
- Client, Redis
- SET lock_key unique_id
- NX EX 30
- ←, OK, 락 획득 성공
- (작업 수행)
- DEL lock_key
- (if value == unique_id)
- 락 해제
- Redlock 알고리즘 (다중 인스턴스):
- Client
- Redis 1, Redis 2, Redis 3
- OK, OK, FAIL
- Redis 4, Redis 5
- OK, OK
- 과반수(3개 이상)에서 락 획득 → 락 성공
- Redlock 순서:
- 현재 시간 기록 (T1)
- 모든 Redis 인스턴스에 순차적으로 락 시도
- 현재 시간 기록 (T2)
- 과반수 성공 && (T2 - T1) < 락 TTL → 락 획득 성공
- 실패 시 모든 인스턴스에서 락 해제

#### ZooKeeper를 이용한 분산 락

- ZooKeeper 분산 락 구현
- ZNode 구조:
- /locks
- /resource_lock
- lock-0000000001, (Client A)
- lock-0000000002, (Client B)
- lock-0000000003, (Client C)
- 락 획득 과정:
- Client A, ZooKeeper
- create /locks/resource_lock/
- lock- (EPHEMERAL +
- SEQUENTIAL)
- ←, /locks/.../lock-0001
- getChildren()
- ←, [lock-0001], 내가 최소값 → 락 획득
- Client B, ZooKeeper
- create lock-0002
- ←, /locks/.../lock-0002
- getChildren()
- ←, [lock-0001, lock-0002], 내가 최소가 아님
- watch(lock-0001), 이전 노드 감시
- (lock-0001 삭제 시 알림)
- ←, 락 획득!

### 리더 선출 (Leader Election)

- 분산 시스템에서 하나의 노드를 리더로 선출하는 과정임.

- 리더 선출 알고리즘
- Bully 알고리즘:
- 가장 높은 ID를 가진 노드가 리더가 됨
- Node 1, Node 2, Node 3(L), Node 4
- X (장애)
- 타임아웃 감지
- ←, Election 메시지
- ←, OK
- Node 4가 더 높은 ID
- → 선거 포기
- ←, Coordinator
- ←, Coordinator
- Node 4가 새 리더

#### Ring 알고리즘

- Ring 선출 알고리즘
- Node 1, →, Node 2
- (ID=1), (ID=2)
- Node 4, ←, Node 3
- (ID=4), (ID=3)
- 선거 과정:
- Node 2가 선거 시작
- Election[2] → Node 3
- Node 3가 자신의 ID 추가 후 전달
- Election[2,3] → Node 4
- Node 4가 자신의 ID 추가 후 전달
- Election[2,3,4] → Node 1
- Node 1이 자신의 ID 추가 후 전달
- Election[2,3,4,1] → Node 2
- Node 2가 리스트 수신 (자신이 시작점)
- → 최대 ID = 4 → Node 4가 리더
- Coordinator[4] 메시지 전파

#### ZooKeeper를 이용한 리더 선출

- ZooKeeper 리더 선출
- /election
- member-0000000001, → Leader (최소 시퀀스)
- member-0000000002, → Follower (watch: 0001)
- member-0000000003, → Follower (watch: 0002)
- 선출 과정:
- 각 노드가 EPHEMERAL_SEQUENTIAL 노드 생성
- 자신의 시퀀스 번호가 가장 작으면 리더
- 아니면 바로 앞 번호 노드를 watch
- watch 대상 노드 삭제 시 다시 확인
- 장애 복구 시나리오:
- Before:, After (Leader 장애):
- member-0001 (Leader), member-0001 X (세션 만료)
- ↓, member-0002, → New Leader
- member-0002 (watching 0001)
- ↓, member-0003 (watching 0002)

### Quorum 기반 일관성

- Quorum 기반 읽기/쓰기
- N = 전체 복제본 수
- W = 쓰기 쿼럼 (쓰기 성공에 필요한 최소 응답 수)
- R = 읽기 쿼럼 (읽기 성공에 필요한 최소 응답 수)
- 강한 일관성 조건: W + R > N
- 예시 (N=3):
- Replica, Replica, Replica
- 1, 2, 3
- W=2, R=2 설정 시:
- 쓰기:, 읽기:
- W, → R1 (성공), R, → R1 (v2)
- r, → R2 (성공), e, → R2 (v2)
- i, → R3 (실패/느림), a, → R3 (응답 대기 안함)
- t, d
- e
- 2개 성공 → OK, 2개 응답 → 최신 값 반환
- W + R = 4 > 3 (N) → 강한 일관성 보장
- 설정별 특성:
- 설정, 특성
- W=1, R=N, 빠른 쓰기, 느린 읽기
- W=N, R=1, 느린 쓰기, 빠른 읽기
- W=R=N/2+1, 균형 잡힌 설정
