# 성능 지표

컴퓨터가 더 빠르다고 할 때는 작업 하나가 빨리 끝난다는 뜻인지, 같은 시간에 더 많은 작업을 처리한다는 뜻인지부터 구분해야 한다. 어떤 지표를 비교하느냐에 따라 최적화할 부분과 하드웨어 선택이 달라지기 때문이다.

## 성능의 정의

응답 시간(Response Time / Latency)은 작업 하나를 완료하는 데 걸리는 시간이다. 개인 컴퓨터나 대화형 시스템을 사용하는 사람에게는 이 시간이 짧아지는 것이 중요하다. 반면 서버나 데이터센터를 운영할 때는 단위 시간에 완료하는 작업 수인 처리량(Throughput / Bandwidth)도 함께 봐야 한다.

실행 시간을 기준으로 성능을 비교하면 `성능_X = 1 / 실행시간_X`로 둘 수 있다. 이때 X가 Y보다 n배 빠르다는 말은 `성능_X / 성능_Y = 실행시간_Y / 실행시간_X = n`이라는 뜻이다.

## CPU 시간 (CPU Time)

프로그램의 시작부터 종료까지 흐른 경과 시간(Elapsed Time / Wall Clock Time)에는 CPU 연산뿐 아니라 I/O 대기와 다른 프로세스가 실행되는 시간도 포함된다. 그중 CPU가 실제로 프로그램 실행에 사용한 부분을 CPU 시간이라고 한다.

CPU 시간은 프로그램 코드를 실행한 사용자 시간(User CPU Time)과 운영체제 커널 코드를 실행한 시스템 시간(System CPU Time)으로 나뉜다. 프로그램이 느릴 때 이 구분을 보면 연산 자체가 오래 걸리는지, CPU 밖에서 기다리는 시간이 긴지 살펴볼 수 있다.

## 클록 사이클과 클록 속도

클록 주기(Clock Period)는 한 사이클에 걸리는 시간이고, 클록 속도(Clock Rate / Frequency)는 1초 동안 반복되는 사이클 수다. 두 값은 `Clock Rate = 1 / Clock Period`의 관계를 갖는다.

예를 들어 3 GHz CPU의 클록은 초당 30억 번 반복되므로, 한 주기는 `1 / (3 × 10⁹) ≈ 0.33 ns`다.

## CPU 성능 공식

CPU 시간은 사용한 클록 사이클 수에 한 사이클의 시간을 곱한 값이다.

`CPU Time = Clock Cycles × Clock Period = Clock Cycles / Clock Rate`

사이클 수를 다시 명령어 수(Instruction Count)와 명령어당 평균 사이클 수(CPI)로 나누면, 같은 시간을 다음과 같이 표현할 수 있다.

`CPU Time = Instruction Count × CPI × Clock Period = (Instruction Count × CPI) / Clock Rate`

따라서 클록 속도만으로 실행 시간을 설명할 수는 없다. 실행하는 명령어 수와 각 명령어를 처리하는 비용도 함께 봐야 한다.

## CPI (Cycles Per Instruction)

CPI는 명령어 하나를 실행하는 데 필요한 평균 클록 사이클 수다. 명령어 종류마다 비용이 다르므로, 각 종류의 실행 횟수를 가중치로 사용한다.

`CPI = (1/IC) × Σᵢ₌₁ⁿ(CPIᵢ × ICᵢ)`

여기서 IC는 전체 명령어 수, CPIᵢ는 i번째 종류의 CPI, ICᵢ는 그 종류의 실행 횟수다. 다음 비율로 명령어를 실행한다고 가정해 보자.

| 명령어 종류 | CPI | 실행 비율 |
| --- | --- | --- |
| ALU 연산 | 1 | 40% |
| Load/Store | 3 | 30% |
| Branch | 2 | 20% |
| Multiply | 4 | 10% |

평균 CPI는 `0.4×1 + 0.3×3 + 0.2×2 + 0.1×4 = 2.1`이다.

## MIPS와 FLOPS

### MIPS (Million Instructions Per Second)

MIPS는 초당 실행한 명령어 수를 백만 단위로 나타낸다.

`MIPS = Instruction Count / (Execution Time × 10⁶) = Clock Rate / (CPI × 10⁶)`

다만 ISA가 다르면 같은 작업에 필요한 명령어 수도 달라진다. 명령어의 종류를 구분하지 않아 NOP도 하나로 세므로, MIPS가 높다는 사실만으로 같은 작업을 더 빨리 끝낸다고 판단하기는 어렵다.

### FLOPS (Floating-Point Operations Per Second)

FLOPS는 초당 부동소수점 연산 수로, 과학·공학 계산의 성능을 표현할 때 주로 사용한다. 단위에 따른 배수는 다음과 같다.

- MFLOPS: 10⁶ FLOPS
- GFLOPS: 10⁹ FLOPS
- TFLOPS: 10¹² FLOPS
- PFLOPS: 10¹⁵ FLOPS
- EFLOPS: 10¹⁸ FLOPS

## Amdahl's Law (암달의 법칙)

시스템의 일부를 빠르게 만들어도 나머지 부분에 걸리는 시간은 그대로 남는다. 암달의 법칙은 이 때문에 전체 성능 향상에 생기는 한계를 설명한다.

`Speedup_overall = 1 / ((1 - F) + F / Speedup_enhanced)`

F는 개선할 부분이 원래 실행 시간에서 차지하는 비율(0 ≤ F ≤ 1)이고, Speedup_enhanced는 그 부분의 성능 향상 배율이다.

프로그램의 80%를 병렬화할 수 있고 나머지 20%는 순차적으로 실행해야 한다고 하자. 병렬 부분을 10배 빠르게 만들면 전체 향상은 `1 / (0.2 + 0.8/10) ≈ 3.57배`다. 원래 시간의 80%가 8%로 줄어도 순차 부분의 20%는 남기 때문이다. 병렬 부분을 아무리 빠르게 만들어도 이 예제의 한계는 `1 / (1 - F) = 5배`다.

## Gustafson's Law (구스타프슨의 법칙)

암달의 법칙이 같은 크기의 문제를 얼마나 빨리 끝낼 수 있는지 묻는다면, 구스타프슨의 법칙은 같은 시간에 문제의 크기를 얼마나 늘릴 수 있는지 살펴본다. 프로세서 수를 늘리면서 병렬 작업의 규모도 키우는 관점이다.

`Speedup = (1 - F) + F × N`

여기서 F는 병렬화 가능한 비율, N은 프로세서 수다. 문제 크기를 고정한 경우와 시간을 고정한 경우는 비교 조건이 다르므로, 두 식이 어떤 질문에 답하는지 구분해서 사용해야 한다.

## Iron Law of Processor Performance

앞서 나눈 CPU 시간의 세 요소는 서로 다른 설계 선택의 영향을 받는다.

- Instruction Count:
  - 영향을 주는 것: 알고리즘, 컴파일러, ISA
- CPI:
  - 영향을 주는 것: 마이크로아키텍처, ISA, 메모리 시스템
- Clock Period:
  - 영향을 주는 것: 마이크로아키텍처, 반도체 기술
단위로도 이 관계를 확인할 수 있다. `명령어 수/프로그램 × 사이클 수/명령어 × 초/사이클`을 곱하면 프로그램당 실행 시간이 남는다.

한 요소를 바꾸면 다른 요소에도 영향을 줄 수 있다. 다음은 이 관계를 설명하는 트레이드오프다.

- 클록 속도↑ → CPI↑ (파이프라인 깊어짐)
- CISC: Instruction Count↓, CPI↑
- RISC: Instruction Count↑, CPI↓

## 벤치마크 (Benchmarks)

실제 성능을 비교할 때는 표준 프로그램인 벤치마크를 사용한다. 벤치마크마다 실행하는 작업이 다르므로, 비교하려는 시스템의 용도와 함께 봐야 한다.

| 벤치마크 | 주요 작업 |
| --- | --- |
| SPEC CPU의 SPECint | 컴파일러·압축 등 정수 연산 |
| SPEC CPU의 SPECfp | 과학 계산·시뮬레이션 등 부동소수점 연산 |
| SPEC JBB | Java 비즈니스 작업 |
| TPC-C | 데이터베이스 트랜잭션 처리 |
| LINPACK | 선형 대수 연산, 슈퍼컴퓨터 순위에 사용 |
| MLPerf | 머신러닝 작업 |
| CoreMark | 임베디드 시스템 작업 |
