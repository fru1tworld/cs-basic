# LR 파싱

LR 파싱은 입력을 왼쪽에서 오른쪽으로 읽으면서 최우단 유도의 역순으로 구문 구조를 만드는 상향식 파싱이다. 스택에 쌓인 기호가 규칙의 우변과 같더라도 곧바로 축약하지 않는다. 현재 상태와 허용된 룩어헤드를 함께 보고 축약할 시점을 결정한다.

## LR 파싱의 기본 원리

LR 파서는 입력을 소비하는 Shift와 이미 읽은 구문을 비단말로 묶는 Reduce를 반복한다. 상태에는 지금까지 읽은 입력이 문법의 어느 위치까지 진행했는지가 담긴다.

이 상태와 스택으로 유효 접두사(Viable Prefix)를 추적한다. 유효 접두사는 우측 문장 형식에서 핸들의 오른쪽 끝을 넘지 않는 접두사다. LR 파서는 좌재귀도 처리할 수 있으며, 복잡한 문법의 상태 계산은 보통 파서 생성기에 맡긴다.

## Shift-Reduce 파싱

Shift는 룩어헤드 토큰을 스택에 넣고 지정된 다음 상태로 이동한다. 이때 입력 토큰 하나를 소비한다.

Reduce는 선택한 규칙의 우변 길이만큼 스택에서 제거하고 좌변 비단말로 바꾼다. 이 과정에서 구문 노드를 만들거나 의미 동작을 실행할 수 있다. 제거 후 남은 상태와 좌변 비단말로 GOTO를 조회해 다음 상태를 결정한다. Reduce는 입력을 소비하지 않으므로 같은 룩어헤드로 여러 번 축약할 수 있다.

시작 규칙의 분석을 마치고 입력 끝을 확인하면 Accept다. 현재 상태와 입력에 허용된 동작이 없으면 Error다. 우변에 해당하는 기호가 스택에 있더라도 더 큰 구문의 일부일 수 있으므로, 룩어헤드로 지금 축약할지 추가 입력을 받을지 판단한다. [Bison 룩어헤드 설명](https://www.gnu.org/software/bison/manual/html_node/Lookahead.html)에서 이 선택 과정을 다룬다.

## 핸들 (Handle)

핸들은 우측 문장 형식에서 특정 규칙으로 축약했을 때 최우단 유도의 바로 이전 단계로 돌아가는 부분 문자열과 그 위치다. 따라서 규칙의 우변과 모양이 같은 부분 문자열이라고 모두 핸들인 것은 아니다. 올바른 유도 순서를 복원하는 위치여야 한다.

LR 파서에서는 상태가 스택 위 기호의 축약 가능 여부를 결정한다. 예를 들어 `T → T * F`의 `*`는 곱셈 토큰으로 문법의 일부이며, 핸들을 판단할 때는 우변 전체와 파싱 문맥을 함께 봐야 한다.

## LR(0) 아이템

아이템은 생성 규칙의 우변에 점을 넣어 인식이 진행된 위치를 나타낸다. `A → α . β`는 `α`를 인식했고 이어서 `β`를 인식해야 한다는 뜻이다. 여기서 점은 실제 입력 토큰이 아니라 파서 생성 과정의 표기다.

점이 맨 뒤에 도달한 완성 아이템은 축약 후보가 된다. 어떤 입력에서 축약을 허용할지는 LR(0), SLR(1), LR(1) 등 테이블 구성 방식에 따라 달라진다.

## 클로저 연산 (Closure)

아이템 집합에 `A → α . B β`가 있으면 다음에 비단말 `B`를 인식해야 한다. 따라서 B의 각 생성 규칙을 점이 맨 앞에 있는 아이템으로 추가한다. 새 아이템에도 같은 과정을 적용해 더 이상 아이템이 늘어나지 않을 때 종료한다.

이렇게 구한 클로저에는 현재 상태에서 시작할 수 있는 하위 구문이 모두 포함된다. 가능한 구문을 확장하는 연산이므로 입력은 소비하지 않는다.

## GOTO 연산

`GOTO(I, X)`는 아이템 집합 I에서 기호 X 바로 앞에 점이 있는 모든 아이템을 모아, 점을 X 뒤로 옮긴 뒤 클로저를 구한 결과다. 조건을 만족하는 아이템 전체를 함께 이동해야 한다.

파서 생성 과정의 GOTO는 단말과 비단말 모두의 상태 전이를 정의한다. 실행 테이블에서는 보통 단말 전이를 ACTION의 Shift로, 비단말 전이를 GOTO 테이블로 나누어 저장한다.

## LR(0) 오토마톤 구성

새로운 시작 규칙을 추가한 확장 문법에서 시작 아이템의 클로저를 초기 상태로 삼는다. 각 상태에서 가능한 문법 기호에 GOTO를 적용하고, 비어 있지 않은 새 아이템 집합을 상태로 등록한다. 이미 등록한 집합이라면 기존 상태를 재사용하며, 새로운 집합이 없을 때까지 반복한다.

상태 번호는 구현이 붙이는 식별자다. 번호 자체보다 어떤 아이템 집합이 한 상태를 이루고 어떤 조건에서 전이가 생기는지를 따라가는 것이 중요하다.

## LR(0) 파싱 테이블

단말을 읽는 전이는 해당 ACTION 칸에 Shift로 등록한다. 시작 규칙 이외의 완성 아이템은 모든 입력 단말과 입력 끝에 Reduce를 등록하고, 확장 시작 규칙의 완성 아이템은 입력 끝에서 Accept를 등록한다.

LR(0)은 룩어헤드에 따라 축약 범위를 좁히지 않는다. 그 결과 같은 칸에 여러 동작이 들어가면 충돌하며, 해당 문법을 LR(0) 방식으로 결정적으로 처리할 수 없다. FOLLOW에 해당하는 토큰에만 Reduce를 넣어 축약 범위를 좁히는 방식이 SLR(1)이다.

## SLR(1) 파서

SLR(1)은 LR(0) 아이템 집합과 상태 전이를 사용하면서, 완성 아이템 `A → α .`의 Reduce를 `FOLLOW(A)`에 해당하는 토큰에만 등록한다. 축약 조건을 좁혀 LR(0)에서 생기던 일부 충돌을 없앤다.

다만 FOLLOW는 문법 전체에서 가능한 뒤따름을 모으므로 특정 상태의 문맥보다 넓을 수 있다. 해당 상태에서는 축약할 수 없는 문맥까지 허용하면 여전히 충돌이 남는다.

## LR(1) 파서

LR(1) 아이템은 생성 규칙과 점 위치에 룩어헤드 단말을 추가한다. `[A → α . B β, a]`를 확장할 때 B의 새 아이템에 전달할 룩어헤드는 `FIRST(βa)`로 계산한다. 완성 아이템은 자신의 룩어헤드에서만 Reduce를 등록하므로 SLR보다 문맥을 정밀하게 구분한다.

그만큼 테이블은 커질 수 있다. LR(0) 아이템 구성이 같아도 룩어헤드가 다르면 별도 상태가 될 수 있기 때문이다. Canonical LR(1)도 모든 문맥 자유 문법을 결정적으로 처리하는 것은 아니다.

## LALR(1) 파서

LALR(1)은 정규 LR(1) 상태 중 룩어헤드를 제외한 LR(0) 구성이 같은 상태를 합치고, 대응하는 아이템의 룩어헤드를 합집합으로 모으는 방식으로 이해할 수 있다. SLR보다 정밀한 룩어헤드를 활용하면서 작은 테이블을 만들 수 있어 Yacc 계열 도구에서 널리 쓰인다.

상태를 합치면 문맥 구분이 약해져 원래 없던 Reduce-Reduce 충돌이 생길 수 있다. Bison은 IELR과 Canonical LR도 지원하므로, 충돌이 LALR의 상태 병합에서 비롯됐는지 확인하면 불필요한 문법 변형을 줄일 수 있다. [Bison 테이블 구성](https://www.gnu.org/s/bison/manual/html_node/LR-Table-Construction.html)에서 각 방식을 다룬다.

## Shift-Reduce 충돌

같은 상태와 룩어헤드에서 Shift와 Reduce가 동시에 후보가 되면 Shift-Reduce 충돌이다. 모호한 연산자 문법이나 중첩 조건문의 `else` 결합에서 나타날 수 있다. 문법 자체의 모호성 외에도 테이블 구성 방식이 문맥을 충분히 구분하지 못해 발생할 수 있다.

Bison은 별도의 우선순위 규칙이 없으면 Shift를 선택한다. 이 기본값이 언어 설계의 의도와 맞는지는 별도로 확인해야 한다. [Bison Shift-Reduce 충돌](https://www.gnu.org/software/bison/manual/html_node/Shift_002fReduce.html)에 기본 선택 규칙이 설명돼 있다.

## Reduce-Reduce 충돌

같은 상태와 룩어헤드에서 둘 이상의 생성 규칙으로 축약할 수 있으면 Reduce-Reduce 충돌이다. 중복된 구문 경로, 빈 문자열을 만드는 대안의 중첩, LALR 상태 병합 등을 확인해야 한다.

다른 축약을 선택하면 같은 입력을 받아들이더라도 AST와 의미 동작의 실행 순서가 달라질 수 있다. Bison은 기본적으로 문법에서 먼저 나온 규칙을 선택하므로, 여기에 의존하면 규칙 순서가 의미를 바꾸게 된다. 충돌 원인을 찾아 문법이나 테이블 구성을 수정해야 한다. [Bison Reduce-Reduce 충돌](https://www.gnu.org/software/bison/manual/html_node/Reduce_002fReduce.html)에서도 이 문제를 설명한다.

## 연산자 우선순위와 결합성

우선순위는 서로 다른 연산자 중 어느 구문을 먼저 묶을지 결정한다. 결합성은 같은 우선순위의 연산자가 이어질 때 왼쪽과 오른쪽 중 어느 쪽부터 묶을지 결정한다.

일반적인 충돌 해결에서는 룩어헤드 연산자의 우선순위가 높으면 Shift하고, 축약 규칙의 우선순위가 높으면 Reduce한다. 우선순위가 같을 때는 왼쪽 결합이면 Reduce, 오른쪽 결합이면 Shift를 선택한다. 비결합 연산의 경우 같은 우선순위의 연쇄 사용을 오류로 처리할 수 있다.

단항 연산자처럼 토큰의 일반적인 우선순위와 규칙의 우선순위가 달라야 한다면 규칙별로 지정해야 한다. 이런 선언은 충돌을 해결할 선택 정책을 제공하며, 문법 자체의 모호성이 자동으로 사라지는 것은 아니다.
