# 문맥 교환

CPU가 Process A를 실행하다 B로 넘어가려면 A의 레지스터, PC, SP 등을 저장하고 B의 상태를 복원해야 한다. 나중에 A가 중단된 지점에서 실행을 이어 갈 수 있도록 하는 이 과정이 문맥 교환이다. 멀티태스킹에 필요하지만 상태를 저장하고 복원하는 비용이 든다.

## 문맥 교환이란?

- CPU가 한 프로세스/스레드에서 다른 프로세스/스레드로 전환하는 과정임.

- Process A (Running), Process B (Ready)
- 인터럽트 발생
- [A의 상태 저장 (PCB)]
- 스케줄러 실행
- [B 선택]
- B의 상태 복원
- Process A (Ready), Process B (Running)

## 문맥 교환 비용 분석

### 직접 비용 (Direct Cost)

- CPU 레지스터 저장/복원: ~수십 나노초
- PCB 갱신: ~수십 나노초
- 메모리 맵 전환: ~수백 나노초
- TLB 플러시 (프로세스 전환 시): ~수 마이크로초

### 간접 비용 (Indirect Cost)

- CPU 캐시 미스: 수십~수백 마이크로초
- TLB 미스: 수백 사이클
- 파이프라인 플러시: 수십 사이클
- 분기 예측 실패: 수십 사이클

## 벤치마크 결과 (2024 기준)

- 최신 Linux 커널 벤치마크 결과:

- 측정 조건: 같은 코어, 핀드 상태:
  - 문맥 교환 시간: 1.2 ~ 1.5 마이크로초
- 측정 조건: 다른 코어로 마이그레이션:
  - 문맥 교환 시간: ~2.2 마이크로초
- 측정 조건: 큰 working set 포함:
  - 문맥 교환 시간: 39 ~ 203 마이크로초
- 측정 조건: Go goroutine 전환:
  - 문맥 교환 시간: ~170 나노초

- 2024년 11월 Linux 커널 최적화: Meta의 Rik van Riel이 `switch_mm_irqs_off` 함수 최적화 패치를 제출하여 CPU 시간의 17%를 차지하던 캐시 라인 경합 문제를 해결했음.

## 문맥 교환 측정 코드

```c
// 컨텍스트 스위칭 시간 측정 (pipe 기반)
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sched.h>
#include <time.h>
#include <sys/wait.h>

#define ITERATIONS 100000

static inline long long get_nanos() {
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return ts.tv_sec * 1000000000LL + ts.tv_nsec;
}

int main() {
    int pipe1[2], pipe2[2];
    char buf;

    pipe(pipe1);
    pipe(pipe2);

    // CPU 0에 고정
    cpu_set_t cpuset;
    CPU_ZERO(&cpuset);
    CPU_SET(0, &cpuset);
    sched_setaffinity(0, sizeof(cpuset), &cpuset);

    pid_t pid = fork();

    if (pid == 0) {
        // 자식 프로세스
        sched_setaffinity(0, sizeof(cpuset), &cpuset);

        for (int i = 0; i < ITERATIONS; i++) {
            read(pipe1[0], &buf, 1);
            write(pipe2[1], "x", 1);
        }
        exit(0);
    }

    // 부모 프로세스
    long long start = get_nanos();

    for (int i = 0; i < ITERATIONS; i++) {
        write(pipe1[1], "x", 1);
        read(pipe2[0], &buf, 1);
    }

    long long end = get_nanos();
    wait(NULL);

    // 2번의 컨텍스트 스위칭 (부모→자식, 자식→부모)
    double ns_per_switch = (double)(end - start) / (ITERATIONS * 2);

    printf("Context switch time: %.2f ns (%.2f us)\n",
           ns_per_switch, ns_per_switch / 1000);

    return 0;
}
```

## 문맥 교환 최소화 전략

- 스레드 풀 사용: 스레드 생성/삭제 오버헤드 감소
- 비동기 I/O 활용: 블로킹으로 인한 스위칭 감소
- CPU 친화성 설정: 캐시 효율성 향상
- 경량 스레드 사용: goroutine, 코루틴 활용

## 문맥 교환 (Context Switching)

- CPU가 한 프로세스/스레드에서 다른 것으로 전환하는 것임.

### 프로세스 문맥 교환

- 프로세스 A 실행
- A의 상태 PCB에 저장
- B의 상태 PCB에서 로드
- 메모리 맵 변경 (페이지 테이블 교체), ← 비용 큼
- TLB 플러시, ← 비용 큼
- 프로세스 B 실행

### 스레드 문맥 교환 (같은 프로세스 내)

- 스레드 A 실행
- A의 레지스터, PC, Stack 저장
- B의 레지스터, PC, Stack 로드
- 스레드 B 실행

- 스레드가 더 빠른 이유:
- 메모리 맵 변경 불필요 (같은 주소 공간)
- TLB 플러시 불필요
- 캐시 히트율 높음

## 컨텍스트란?

- 프로세스가 실행 중일 때 CPU와 메모리에 있는 모든 상태 정보임.

## CPU 컨텍스트

- CPU 레지스터
- PC (Program Counter), 다음 실행할 명령어 주소
- SP (Stack Pointer), 현재 스택 위치
- BP (Base Pointer), 스택 프레임 기준 주소
- General Purpose Regs, 연산용 레지스터
- (RAX, RBX, RCX, ...), (x86-64 기준 16개)
- Flags/Status Register, 상태 플래그
- Floating Point Regs, 부동소수점 연산용
- SIMD Registers (XMM), 벡터 연산용

## 메모리 컨텍스트

- 메모리 관리 정보
- 페이지 테이블 베이스 레지스터 (CR3)
- 메모리 맵 정보
- 세그먼트 레지스터

## PCB에 저장되는 정보

```c
// Linux task_struct 주요 필드 (간략화)
struct task_struct {
    volatile long state;           // 프로세스 상태
    pid_t pid;                     // 프로세스 ID
    struct mm_struct *mm;          // 메모리 디스크립터

    struct thread_struct thread;   // CPU 레지스터 상태
    /*
     * thread_struct에 저장되는 정보:
     * - sp (stack pointer)
     * - 기타 CPU 레지스터들
     * - FPU 상태
     */

    struct files_struct *files;    // 열린 파일 테이블
    struct signal_struct *signal;  // 시그널 정보
    // ...
};
```

## 문맥 교환 과정

### 상세 과정

- 문맥 교환 과정
- 트리거 발생 (인터럽트, 시스템 콜, 스케줄러)
- 2.
- 현재 프로세스(A) 상태 저장
- 범용 레지스터 → A의 커널 스택
- PC, SP → A의 task_struct
- 플래그 레지스터 저장
- FPU/SIMD 상태 저장 (lazy saving)
- 3.
- 스케줄러 호출
- 다음 실행할 프로세스(B) 선택
- 실행 큐에서 B 선택
- 4.
- 메모리 컨텍스트 전환
- 페이지 테이블 교체 (CR3 레지스터)
- TLB 플러시 (또는 ASID 사용)
- 5.
- 새 프로세스(B) 상태 복원
- B의 task_struct → PC, SP
- B의 커널 스택 → 범용 레지스터
- 플래그 레지스터 복원
- 프로세스 B 실행 시작

### Linux의 context_switch() 함수

```c
// kernel/sched/core.c (개념적 코드)
static inline struct rq *
context_switch(struct rq *rq, struct task_struct *prev,
               struct task_struct *next)
{
    // 1. 메모리 컨텍스트 전환 준비
    prepare_task_switch(rq, prev, next);

    // 2. 메모리 맵 전환 (페이지 테이블)
    if (!next->mm) {
        // 커널 스레드인 경우
        next->active_mm = prev->active_mm;
    } else {
        // 유저 프로세스인 경우
        switch_mm(prev->active_mm, next->mm, next);
    }

    // 3. CPU 컨텍스트 전환 (아키텍처 의존적)
    switch_to(prev, next, prev);

    return rq;
}
```

## 프로세스 vs 스레드 문맥 교환

### 프로세스 문맥 교환

- 프로세스 A → 프로세스 B
- 저장/복원 대상
- 가능 CPU 레지스터 (전체)
- 가능 페이지 테이블 (CR3 교체)
- 가능 TLB 플러시
- 가능 캐시 무효화 (일부)
- 가능 파일 디스크립터 테이블 (간접적)
- 가능 시그널 핸들러
- 비용: 높음 (수 마이크로초)

### 스레드 문맥 교환 (같은 프로세스 내)

- 스레드 A → 스레드 B (같은 프로세스)
- 저장/복원 대상
- 가능 CPU 레지스터
- 가능 스택 포인터
- 가능 TLS (Thread Local Storage)
- 불가 페이지 테이블 (동일)
- 불가 TLB 플러시 불필요
- 불가 캐시 무효화 최소화
- 불가 파일 디스크립터 (공유)
- 비용: 낮음 (수백 나노초)

### 비용 비교

- 레지스터 저장/복원:
  - 프로세스 전환: 필요
  - 스레드 전환: 필요
- 페이지 테이블 교체:
  - 프로세스 전환: 필요 (CR3 변경)
  - 스레드 전환: 불필요
- TLB 플러시:
  - 프로세스 전환: 필요
  - 스레드 전환: 불필요
- 캐시 영향:
  - 프로세스 전환: 큼 (Cold)
  - 스레드 전환: 작음 (Warm)
- 예상 시간:
  - 프로세스 전환: 1~10 μs
  - 스레드 전환: 0.1~1 μs

## 문맥 교환 오버헤드

### 직접 비용 (Direct Cost)

- 직접 비용 = 실제 전환 작업에 드는 시간
- 레지스터 저장, (~100 cycles)
- 스케줄러 실행, (~200 cycles)
- 페이지 테이블 전환, (~50 cycles)
- 레지스터 복원, (~100 cycles)
- 총 직접 비용: ~500-1000 CPU cycles
- (약 0.2-0.5 μs @ 2GHz)

### 간접 비용 (Indirect Cost)

- 간접 비용 = 캐시/TLB 미스로 인한 추가 지연
- TLB 미스 비용
- TLB 플러시 후 페이지 테이블 워킹:
- 4단계 페이지 테이블 × 메모리 접근
- 최대 수백 cycles per TLB miss
- 캐시 미스 비용
- 새 프로세스의 데이터가 캐시에 없음:
- L1 miss: ~4 cycles
- L2 miss: ~12 cycles
- L3 miss: ~40 cycles
- RAM 접근: ~100+ cycles
- 총 간접 비용: 수천~수만 cycles
- (직접 비용보다 훨씬 큼!)

### 측정 방법

```c
// 간단한 컨텍스트 스위칭 시간 측정
#include <time.h>
#include <unistd.h>

int main() {
    int pipe_fd[2];
    pipe(pipe_fd);

    struct timespec start, end;
    char buf;

    pid_t pid = fork();
    if (pid == 0) {
        // 자식: 읽고 쓰기 반복
        for (int i = 0; i < 10000; i++) {
            read(pipe_fd[0], &buf, 1);
            write(pipe_fd[1], &buf, 1);
        }
    } else {
        // 부모: 시간 측정
        clock_gettime(CLOCK_MONOTONIC, &start);

        for (int i = 0; i < 10000; i++) {
            write(pipe_fd[1], &buf, 1);
            read(pipe_fd[0], &buf, 1);
        }

        clock_gettime(CLOCK_MONOTONIC, &end);

        double elapsed = (end.tv_sec - start.tv_sec) * 1e6 +
                        (end.tv_nsec - start.tv_nsec) / 1e3;
        printf("Context switch time: %.2f μs\n", elapsed / 20000);
    }
    return 0;
}
```

## TLB와 문맥 교환

### TLB 플러시 문제

TLB에는 이전 프로세스의 주소 변환 정보가 남아 있을 수 있다. 새 프로세스가 같은 가상 주소를 사용하더라도 대응하는 물리 주소는 다를 수 있으므로, 이전 변환을 그대로 쓰면 잘못된 위치에 접근한다. 이를 막기 위해 TLB를 비우거나, 아래의 ASID처럼 주소 공간을 구분하는 정보가 필요하다.

### ASID (Address Space ID)

ASID는 TLB 엔트리에 가상 페이지 번호와 물리 프레임뿐 아니라 주소 공간의 ID도 기록한다. 전환할 때 현재 ASID를 바꾸면 다른 ASID의 엔트리를 남겨 둔 채 새 프로세스의 변환 정보만 사용할 수 있다. x86-64에서는 PCID(Process Context ID), ARM에서는 ASID를 사용한다.

## 문맥 교환 트리거

- 문맥 교환 발생 시점
- 타임 슬라이스 만료
- 타이머 인터럽트 발생
- 스케줄러가 다음 프로세스 선택
- I/O 대기
- 프로세스가 블로킹 I/O 호출
- 자발적으로 CPU 양보
- 높은 우선순위 프로세스 도착
- 선점형 스케줄링에서 발생
- 현재 프로세스 중단, 높은 우선순위 실행
- 동기화 대기
- 뮤텍스, 세마포어 대기
- 프로세스 블록 상태로 전환
- 명시적 양보 (yield)
- sched_yield() 호출
- 자발적 CPU 양보

## 최적화 기법

### Lazy FPU Context Switching

- 아이디어: 모든 프로세스가 FPU를 사용하지는 않음
- 전통 방식:
- 문맥 교환 시 항상 FPU 레지스터 저장/복원
- → 불필요한 오버헤드
- Lazy 방식:
- 문맥 교환 시 FPU 저장 안 함
- FPU 비활성화 상태로 설정
- 새 프로세스가 FPU 사용 시도
- #NM Exception 발생
- 그때 이전 FPU 상태 저장, 새 상태 로드
- FPU 활성화
- 결과: FPU 미사용 프로세스는 오버헤드 없음

### Kernel Same-Page Merging (KSM)

- 동일 페이지 공유로 메모리 절약 + TLB 효율 향상
- 가상화 환경에서 유용:
- VM 1, VM 2
- [동일한 라이브러리 페이지] [동일한 라이브러리 페이지]
- 단일 물리
- 프레임
